# Storage contract

`Storage` is exported from `@walq/core/storage`; its types are defined in [`packages/core/src/storage.ts`](../packages/core/src/storage.ts). This contract specifies the behavior adapters must preserve.

## Shared rules

- Queue matching is exact. Every read, mutation, claim, and cleanup is scoped to the requested queue; queue names share no job state.
- Timestamps are nonnegative safe-integer Unix milliseconds; priorities are signed safe integers; lease durations, attempts, and limits are positive safe integers. Retention bounds are `null` or nonnegative safe integers. Computed expiries must remain safe. The caller supplies `now`; adapters do not establish a shared clock. Distributed callers need synchronized clocks.
- Names and deduplication keys are nonempty strings; data is serialized JSON. Invalid inputs reject without mutation. Error classes and messages are unspecified.
- Persist mutations before resolving. Invalid input and storage/transport errors reject; they are not `false` or `lease_lost`. A transport error may leave commit status uncertain, so enqueue without a dedupe key is not idempotent.
- IDs and lease tokens are opaque. Generate unique IDs and a fresh token per successful claim. Delivery is at-least-once: tokens protect queue state, not handler side effects.

## Operations

- **`enqueue(input)`** creates a pending job with a generated ID, `createdAt = now`, the supplied `priority`, `attemptsMade = 0`, and `error = null`. `availableAt` may be in the past. Without `dedupe`, each call inserts an independent job. With a nonempty `dedupe` key, return the existing job unchanged if the same key is already persisted in this queue, regardless of status; do not replace its payload or options or attach the requested group to it. Keys are unique per queue, and storage must enforce uniqueness under concurrent enqueue calls. An optional group has a nonempty `id` and positive safe-integer `concurrency`; its shorthand string means concurrency 1. Group IDs and their fixed concurrency are scoped to the queue. The first newly inserted job establishes that configuration; conflicting concurrency is rejected, including after all jobs in the group have been deleted. A duplicate enqueue validates a supplied concurrency against an existing group configuration but does not establish an otherwise-unused group.
- **`enqueueMany(inputs)`** follows `enqueue` in input order. Validate all inputs before mutation; commit all inserts atomically or none. Repeated dedupe keys in a batch resolve to the first existing or newly inserted job ID, and results remain in input order. Empty input returns `[]`.
- **`pause({ queue })` / `resume({ queue })`** persist whether new claims are enabled for that exact queue. Both are idempotent and resolve only after the state is committed. The pause state survives adapter reconnection and process restart. Enqueue and other job mutations remain available while paused. A pause is serialized atomically with claim transactions: once pause resolves, later `claim` and `claimQueues` requests recover expired leases if needed but return no new jobs for that queue. Recovery is intentionally not suspended; expired jobs become pending or failed per the normal attempt rule. Existing live leases remain eligible for heartbeat, completion, and failure. A paused queue must not materialize durable schedules. Resume enables subsequent claims and schedule materialization; workers in the same coordinator are woken, while other processes notice resume through normal polling.
- A dedupe key remains reserved for as long as its job row exists. Physical deletion by `remove` or terminal retention cleanup releases it; status changes do not. Group configurations outlive jobs and are not removed by job deletion or retention cleanup; this keeps a group's concurrency stable across retries, deduplication, and database reopen.
- **`claim(input)`** atomically recovers expired leases for that queue and claims up to `limit` due jobs unless the queue is paused. Expiry is `expiresAt <= now`; recover all expired jobs even when no job is returned or the limit is reached, including when paused. With attempts remaining, recovery returns a job to pending at its old expiry; otherwise it marks it failed. It preserves the last error and invalidates the old token, without overwriting a concurrent heartbeat or completion. Expiry alone does not change stored state. A grouped job can be claimed only while fewer than its group's configured number of jobs are active in that queue. The check and claims are one atomic storage operation, including multi-job and grouped claims, so separate SQLite connections share the same limit. Saturated groups are skipped while other eligible groups and ungrouped jobs remain claimable. Any transition out of active state releases that group's slot.
  - Claim only pending jobs with `availableAt <= now` and `attemptsMade < attempts`, ordered by `priority` descending, then `availableAt`, then original enqueue order. Thus priority only orders jobs that are already due. A deduplicated enqueue does not create a new enqueue position; retries and reschedules retain the job's original position. Increment `attemptsMade` and assign a fresh token with `expiresAt = now + leaseDuration` atomically. Each claim is atomic; handler execution and completion order across workers are not guaranteed. An attempt counts a claim, including one whose handler never starts; `attempts` includes the initial claim.
- **`claimQueues?(requests)`** is optional; results correspond to requests in order, and each request has standalone `claim` semantics, including group limits and pause state. Validate all requests before mutation. Requests for the same queue see earlier changes. An adapter may commit the group together or independently; callers must not assume cross-request atomicity. Empty input returns `[]`.
- **`inspect` / `list`** return queue-scoped snapshots, including priority; `inspect` returns `null` for an absent ID or one in another queue. `list` requires one of `pending`, `active`, `completed`, `failed`, or `cancelled`. Its order is deterministic: pending by availability ascending, then original enqueue order; active by expiry ascending, then binary ID; terminal statuses by finish time descending, then binary ID. Pending jobs are listed by availability, not by the priority order used when claiming due jobs. Reads are not reservations. Expired active jobs stay active until claimed for recovery. Snapshots never expose lease credentials.
- **`count({ queue })`** returns persisted counts for all five statuses (`pending`, `active`, `completed`, `failed`, and `cancelled`), including zeroes. It is a read-only snapshot: it does not recover expired leases, so expired active jobs remain counted as active until a claim recovers them. Completed and failed counts reflect rows still persisted after retention cleanup; they are not lifetime totals.
- **`retry`** accepts failed jobs only, makes them pending at `now`, clears `finishedAt`, and preserves `attemptsMade` and error. If exhausted, set `attempts = attemptsMade + 1` to grant one more claim; reject on safe-integer overflow.
- **`cancel`** accepts pending jobs only and records a terminal `cancelled` state. **`reschedule`** changes availability of pending jobs only; past times are valid. **`remove`** physically deletes any job except active ones, even if an active lease has expired but is not yet recovered.
- Retry, cancel, reschedule, and remove return `false` for a missing job, another queue, or an incompatible state; otherwise `true`. Invalid input and storage errors reject.
- **`complete`, `fail`, `heartbeat`** require an active job, the current token, and `expiresAt > now`. Return `lease_lost` without mutation otherwise; storage errors reject. Completion marks the job completed and invalidates its lease. Failure records its error and returns the job to pending at `retryAt` only if non-null and attempts remain; `retryAt <= now` is valid. Otherwise it marks the job failed. `applied` means the mutation was recorded, not that failure was retried. Heartbeat retains the token and sets expiry to `max(current expiry, now + leaseDuration)`; it cannot revive an expired lease.
- **`cleanup`** atomically deletes up to `limit` completed or failed jobs from the requested queue; pending, active, and cancelled jobs are excluded. Per status, `count` keeps the newest N and `maxAge` removes rows with `finishedAt < now - maxAge`; a row is eligible if it exceeds either bound. `null` disables a bound; two null bounds keep all rows. Delete oldest eligible rows first, ordered by finish time then binary ID. Return `{ removed, more }`, where `more` may conservatively be true; repeated bounded calls must converge and remain restart-safe. Work must depend on the batch limit and retention bounds, not total history.
- **Durable schedules** are an optional `Storage` capability so existing adapters remain compatible. Implement `upsertSchedule`, `getSchedule`, `removeSchedule`, and `materializeSchedules` together; a queue using an adapter without these methods rejects schedule API calls and workers simply skip schedule polling. Schedule identity is the exact `(queue, id)` pair. Upserting identical serialized data and repeat options must return the existing schedule without changing `nextRunAt`; changed data or options set the next occurrence from the supplied `now`. `every` is a positive safe-integer millisecond interval. `cron` uses cron-parser expressions in UTC and selects the first occurrence strictly after `now`. Reads and removals are queue-scoped. Removing or updating a schedule never changes already-materialized jobs.
- **`materializeSchedules({ queue, now, attempts })`** atomically materializes a bounded batch of due schedules at most once each per call and advances their `nextRunAt` in the same transaction. If the queue is paused, return `0` without advancing schedules or creating jobs. Repeated calls must eventually process all due schedules. Create a standard pending job with a fresh unique ID, `createdAt = now`, `availableAt` equal to the due occurrence, priority `0`, the supplied attempts, and no dedupe key or group. Skip missed occurrences rather than creating a catch-up burst; the new `nextRunAt` must be strictly after `now` (for intervals preserve the original interval phase). Concurrent callers, including callers using different SQLite connections, must not create duplicate jobs or advance a schedule without its job. A failure rolls back both job creation and schedule advancement. Return the number of jobs materialized.

For terminal jobs, set `finishedAt` to the operation's `now`; pending and active jobs have `finishedAt = null`. Completion preserves attempt history and the last error; failure and expiration recovery do not increment attempts. Cancelled jobs are not covered by automatic retention.
